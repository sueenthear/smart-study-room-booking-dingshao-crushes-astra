## 一、需求与接口的对应关系

| 需求编号 | 需求摘要 | 落在哪个接口 | 说明 |
| --- | --- | --- | --- |
| FR-01 | 学生登录，受限账号可登录但不可预约，需显示原因与解封日期 | API-01、API-05 | 登录返回受限信息；预约入口二次拦截 |
| FR-02 | 管理员登录进入工作台 | API-01 | 与 FR-01 共用登录，role 区分 |
| FR-03 | 座位与教室查询：按名称/区域/设施搜索，按状态筛选 | API-03 | 服务端返回全量 + 状态标签，筛选在前端完成 |
| FR-04 | 创建预约：校验资格、座位状态、时段合法性、时段冲突 | API-05 | 校验顺序见 API-05 |
| FR-05 | 取消预约（仅"已预约"可取消），取消后释放座位 | API-04、API-06 | 先能查到自己的预约，再发起取消 |
| FR-06 | 签到：记录时间，迟到超 15 分钟记违约，超结束时间不得签到 | API-06 | 签到与违约在同一迁移内完成 |
| FR-07 | 签退：记录时间与提前分钟数，转已完成 | API-06 | 与签到共用状态变更接口 |
| FR-08 | 超时未签到处置：自动置违约并释放座位 | API-06（部分） | 目前靠管理员或手工触发，没有定时任务 |
| FR-09 | 座位状态与报修：维修中、有活动预约禁报修、维修完成恢复 | API-07 | 报修前查活动预约与占用状态 |
| FR-13 | 履约信用：违约扣分，90 天不计入 | API-06（副作用） | 记违约时同步重算信用分 |
| FR-14 | 黑名单：记录原因期限，到期自动恢复 | API-01、API-05 | 登录展示、预约拦截，到期在预约入口顺带解除 |
| NFR-01 | 并发一致性：同座位同时段只允许一条成功 | API-05 | BEGIN IMMEDIATE 事务（ADR-002） |
| NFR-02 | 权限隔离：学生调管理接口必须被拒绝 | 全部 | 服务端鉴权 + 角色校验（ADR-003） |
| NFR-07 | 数据与隐私：密码哈希、敏感字段脱敏 | API-01、API-04 | 会话 token 存哈希；账号快照剔除密码 |

本阶段没覆盖的：FR-10 教室管理、FR-11 学生管理、FR-12 投诉回复、FR-15 运营统计属 S2；FR-16 没有独立审计接口，目前只有页面提示；FR-17 关闭教室未做。

## 二、接口契约

### API-01 登录

**需求依据**
- FR-01：学号＋密码登录；受限账号可登录但不可预约，需显示限制原因与解封日期；
- FR-02：管理员以管理账号进入工作台；
- FR-14：黑名单需记录原因、期限与解封日期；
- AC-01：登录后进入学生工作台，受限账号显示原因与解封日期；
- Q-01：本期不接学校统一身份认证，按本地账号交付、预留对接点（已在架构确认与决策记录 §5 定稿）。

**设计理由**
- 登录响应直接带回 `blacklisted` / `blacklisted_until`，满足 FR-01"登录后就能看到限制原因与解封日期"，前端不必为了一句提示再查一次账号；
- 请求体带 `role`，对应 FR-01 / FR-02 两个入口；但权限不按前端传的 role 算，服务端按账号实际角色签发会话（NFR-02）；
- token 只存哈希（ADR-003），对应 NFR-07；
- 登录时只清理已过期的会话，不做"同账号顶掉旧会话"：允许多端同时登录，退出登录只失效当前这一个 token（见 API-02）。

**契约**
- 方法与路径：POST /api/auth/login
- 调用者与权限：所有人（无需登录）
- 请求体：account、password、role（"student" 或 "admin"）
- 成功响应：
  - 学生：200，返回 token、role、id、name、account、blacklisted、blacklisted_until、message（受限时 message 为"登录成功，账号当前受限"）
  - 管理员：200，返回 token、role、name、account、message（没有黑名单字段，管理员账号不参与预约）
- 失败响应：401 账号或密码错误（学生、管理员同此逻辑）
- 测试关联：TC-I1（登录建会话）、TC-U13~U18（Bearer 头解析）、TC-U29 / U30（账号快照脱敏）
- 已知限制：密码仍是明文比对（ADR-005 暂缓），不影响本接口契约，属 NFR-07 未满足项。

### API-02 退出登录

**需求依据**
- NFR-02：会话要能主动失效，否则共用设备时收不回权限；
- ADR-003：会话表是权限判定的唯一依据，退出即删会话。

**设计理由**
- 不搞 token 黑名单，直接删服务端会话行。服务端是唯一判定源，删了就失效，不会出现"客户端删了 token、服务端还认"的窗口；
- 没有请求体，只认请求头里的 token，避免传错账号误删别人的会话。

**契约**
- 方法与路径：POST /api/auth/logout
- 调用者与权限：任何已登录用户
- 请求体：无
- 成功响应：200 {"message": "已退出登录"}，会话立即失效
- 失败响应：401 未携带有效 token
- 测试关联：TC-I1（登出后原 token 立即失效）

### API-03 座位列表

**需求依据**
- FR-03：座位与教室查询，按名称、区域、设施搜索，按状态筛选，展示教室容量与开放状态；
- ST-10 / ST-11：座位"可预约 ↔ 使用中"由签到、签退驱动；
- BR-16 第一层（新增规则，随 Q/BR 台账入库）：座位状态只反映"此刻是否有人在用"，不反映"是否被预约占用"；
- AC-02 / AC-03：预约前要看到座位当前状态才能判断能不能订。

**设计理由**
- 返回里同时给 `status`（枚举）和 `status_label`（中文），省得前端各自维护一套中文名、显示不一致；
- 带 `classroom_name` 是为了 FR-03 按教室筛选，前端一次拿到就能分组；
- 服务端不做筛选参数：座位量很小（演示数据 12 个，一栋楼也就几十个），全量返回更简单，筛选放前端。以后座位多了再在 S2 加 query 参数，不改现有契约；
- 不因为"有预约"就把座位标成占用（BR-16 第一层），否则会出现座位显示使用中、实际没人的情况。

**契约**
- 方法与路径：GET /api/rooms
- 调用者与权限：所有人（当前代码不要求登录）
- 请求参数：无
- 成功响应：200，座位数组，每条含 id、name、status（open / occupied / maintenance）、status_label、classroom_name、features
- 失败响应：无特殊失败分支
- 隐私注意：对未登录开放，只返回座位信息，无个人数据（NFR-07）
- 与需求的差异：FR-03 的搜索/筛选由前端在返回数据上完成，服务端没有筛选参数。
- 测试关联：TC-I7、TC-Z30（字段齐全、状态标签与状态值一致）、TC-Z16 / TC-Z17（教室容量汇总）

### API-04 预约列表

**需求依据**
- FR-05 / FR-06 / FR-07：取消、签到、签退都要先定位到"我的预约"，本接口是这三个动作的入口；
- NFR-02：学生只能看本人数据；
- NFR-07：返回字段做最小化，不外泄他人手机号等敏感信息；
- 管理员可按 user_id / status 筛选，用于 FR-11（学生管理）和 FR-15（运营统计）的数据查看。

**设计理由**
- 权限判断放服务端，不靠前端只查自己的 id：学生传别人的 `user_id` 直接 403（V-01 已修）；
- 管理员用同一个接口加筛选参数，不再单开一个"管理端预约列表"：同一份数据、同一套状态标签，避免两处实现不一致；
- 返回里带 `user_name`、`student_no`、`room_name`、`status_label`，列表页不用再关联查询（页面每 10 秒刷新，少发请求）。

**契约**
- 方法与路径：GET /api/bookings
- 调用者与权限：需登录。学生只能看本人（传他人 user_id 返回 403）；管理员可看全部，可按 user_id、status 筛选
- 请求参数（可选）：status、user_id（仅管理员有效）
- 成功响应：200，预约数组，含预约字段 + user_name、student_no、room_name、status_label
- 失败响应：401 未登录；403 学生查他人数据
- 已知限制：FR-16 的"通知到人"没做，本接口只提供状态，通知仍靠页面提示。
- 测试关联：TC-I4（学生只见本人）、TC-I5（学生传他人 user_id 返回 403）

### API-05 创建预约

**需求依据**
- FR-04：选择座位与时段创建预约；校验用户资格、座位状态、时段合法性（结束晚于开始、不跨零点）、时段冲突；
- BR-01：同一座位同一时段至多一条有效预约；
- BR-02：同一学生同一时段不得有多条冲突预约（当前未实现）；
- BR-03：维修中的座位不可预约；
- BR-11：受限账号不可新建预约；
- BR-14：时段按 [开始, 结束) 判定，不跨零点；
- BR-15：单次 ≤4 小时、每日 ≤2 次（按人计）、提前 ≤7 天（已于 2026-11-26 定稿，见架构确认与决策记录 §2.4；状态"已决定待同步"）；
- ST-01：提交预约的合法迁移；AC-02 / AC-03 / AC-12；
- NFR-01：并发一致性。

**设计理由**
- 校验顺序是：用户和座位存在 → 座位状态 → 账号资格 → 时间格式 → 结束晚于开始 → 时段冲突。先看资源在不在、能不能用，再看下单的人有没有资格，最后才扫冲突；冲突查询代价最高，放最后能省掉大部分无效查询。每条失败都回具体原因，对应 FR-04；
- 冲突用半开区间判断（已有开始 < 新结束 且 已有结束 > 新开始），依据 BR-14：09:00–10:00 和 10:00–11:00 不算冲突，紧邻时段可以连着订；
- 查冲突和插入放在同一个 `BEGIN IMMEDIATE` 事务里（ADR-002）。BR-01 的唯一性不能只靠先查后写，事务锁把这两步绑成一步，100 线程并发只有一条成功（AC-12）；
- 学生传的 `user_id` 不作数，以登录身份为准，防止替别人下单（NFR-02）；管理员代订时才用请求里的 user_id（ST-07）；
- 过去时间、超过 4 小时、提前超过 7 天都不校验：BR-15 三个数值虽已于 2026-11-26 定稿（≤4h／≤2 次／≤7 天，见架构确认与决策记录 §2.4），但状态为"已决定待同步"、实现暂缓（ADR-004），本阶段不写成硬约束，待同步落地后再校验。

**契约**
- 方法与路径：POST /api/bookings
- 调用者与权限：需登录。学生只能给自己预约；管理员可代任意学生预约（user_id 生效）
- 请求体：user_id（必填字段，学生登录时其值被忽略）、room_id、start_at、end_at
- 成功响应：200 {"id": 预约号, "message": "预约创建成功"}，初始状态 booked
- 失败响应（按代码检查顺序）：
  - 404 用户或座位不存在
  - 409 座位不是 open 状态
  - 400 账号被拉黑（附解封提示）
  - 400 时间格式不正确
  - 400 结束时间必须晚于开始时间
  - 409 该座位在此时段已有预约
- 已知限制（ADR-004、Q-02）：过去时间、单次超 4 小时、提前超 7 天不拦截；BR-02（一人同时段多订）没校验，S2 补。
- 测试关联：TC-Z01~Z05（创建校验）、TC-Z21 / Z22（AC-02、座位不被预约占用）、TC-Z26（维修中拒约）、TC-Z29（时间格式/倒挂）、TC-I6（未登录 401）、TC-I8~I12（冲突与并发）、TC-I17（管理员代订归属）

### API-06 预约状态变更（取消 / 签到 / 签退 / 违约）

**需求依据**
- FR-05：仅"已预约"可取消，取消后释放座位；BR-06；ST-02；AC-04；
- FR-06：签到记录时间，迟到超 15 分钟登记违约，超过结束时间不得签到；BR-07；ST-03；AC-05；Q-05 已关闭（2026-11-26 确认维持 15 分钟、取 >15，见 evidence/Q-05_确认记录.md）；
- FR-07：签退记录时间与提前分钟，转已完成；BR-08；ST-05；AC-06；
- FR-08：超时未签到处置（部分实现，靠本接口的 violation 迁移手工触发，没有定时扫描）；ST-04；
- BR-05：状态只能沿允许路径迁移，非法迁移一律拒绝（ST-08 已完成→已预约、ST-09 已取消→使用中）；
- BR-09 / FR-13：违约扣 0.4 分、下限 1.0、90 天不计入；
- BR-16 第二、三层：取消只让该时段不再占用、不改变座位状态；任何操作不得把被"使用中"预约占用的座位改为"可预约"；
- NFR-01：状态迁移要在事务内完成，避免并发下状态与座位不同步。

**设计理由**
- 五种目标状态共用一个接口（checked_in / completed / cancelled / violation，booked 状态则拒绝）：状态机是一张转移表，集中在一处实现，避免"取消走一个接口、签退走另一个接口"两套规则各写一遍；非法迁移由转移表统一拒绝（BR-05）；
- 学生只能选 checked_in / completed / cancelled，`violation` 只有管理员能设。违约是处置权，学生不能自己给自己记（ST-06 执行角色是管理员）；
- 签到和座位占用放在同一事务：ST-10 要求签到后座位变"使用中"，分开写会出现"预约已经签到、座位还显示可预约"的中间状态；
- 释放座位只对 occupied 生效（SQL 带 `AND status = 'occupied'`）。这是 BR-16 第三层不变量对应的实现：取消一笔未来预约时，如果这个座位正被另一笔已签到预约占着，不能被误放回"可预约"；
- 迟到只在签到那一刻算一次（late_minutes > 15 才写违约），避免重复登记（ST-06：同一预约只登记一次）；
- 签退记 early_minutes 但不扣分，BR-08 规定早退只记录、不参与信用计算。

**契约**
- 方法与路径：PATCH /api/bookings/{booking_id}/status?status=目标状态
- 调用者与权限：需登录。学生只能操作本人预约，且只能改为 checked_in / completed / cancelled（403）；管理员可用全部状态
- 状态流转规则（以王锦添的状态机为准）：
  - booked → checked_in（签到）/ cancelled（取消）/ violation（违约）
  - checked_in → completed（签退）/ violation
  - completed、cancelled、violation 为终态（409）
- 成功响应：200 {"message": ...}
- 失败响应：400 不支持的状态；404 预约不存在；403 非本人或越权状态；409 状态流转不合法 / 座位非 open 不能签到 / 预约时段已结束不能签到
- 关键设计：签到记 late_minutes、超 15 分钟写违约并同步信用分；签退记 early_minutes；签到置座位 occupied，取消/签退/违约在座位为 occupied 时释放
- 已知限制：没有定时任务，FR-08 的自动处置需人工或脚本触发。
- 测试关联：TC-Z06~Z11（五种迁移与非法迁移）、TC-Z23~Z25（签到占用座位、迟到违约）、TC-I13~I16（取消/签退/终态/越权）、TC-I18~I20（迟到 30 分钟违约扣分、提前签退释放座位）

### API-07 座位报修与恢复（管理员）

**需求依据**
- FR-09：座位可置维修中；有活动预约时禁止直接报修；维修完成可恢复；
- BR-04：有活动预约的座位不可直接报修；ST-12 / ST-13 / ST-14；AC-07 / AC-08；
- BR-12 / BR-13：教室容量等于座位数；教室存在非维修座位即为开放，报修和恢复都会改这两个值；
- NFR-02：仅管理员可操作；NFR-06：维修要能回溯（目前只记 status_note 和时间）。

**设计理由**
- 报修前查两类冲突：座位本身是 occupied（有人正在用）就拒绝；存在未结束预约（booked / checked_in 且 end_at 未到）也拒绝，并告诉管理员有几条。前者对应 ST-12 的"无活动预约"，后者是 BR-04；分开判断是为了给不同提示（"先签退" vs "先取消预约"），对应 AC-07；
- 只允许手动切 open / maintenance。occupied 是签到产生的系统状态，管理员手改会造出"座位使用中但没有对应预约"的脏数据（BR-16 第三层）；
- 教室容量和开放状态在同一事务里同步（BR-12 / BR-13 要求教室状态由座位汇总），否则会出现"座位已维修、教室还显示开放"；
- 恢复时 note 为空就写默认说明"维修完成，恢复可用"，ST-13 要求填恢复说明，保证能追溯（NFR-06）。

**契约**
- 方法与路径：PATCH /api/rooms/{room_id}/status
- 调用者与权限：仅管理员（未登录 401，学生 403）
- 请求体：status（只允许 "open" 或 "maintenance"）、note（可空）
- 成功响应：200，报修返回"座位已进入维修状态"，恢复返回"座位已恢复为可预约"
- 失败响应：400 其他状态值；404 座位不存在；409 使用中的座位不能报修；409 还有未结束预约不能报修；409 非 open/maintenance 状态不能恢复
- 关键设计：报修查活动预约并提示条数；状态更新与教室容量同步在同一事务
- 测试关联：TC-Z12~Z15（座位状态流转）、TC-Z27 / Z28（报修拦截与恢复）、TC-I3（学生调用 403）、TC-I11（维修中座位不可约）

**功能需求**

| 编号 | 原文 |

| FR-05 | 仅"已预约"状态可取消，取消后释放座位 |
| FR-06 | 记录签到时间；迟到超过 15 分钟登记违约；超过结束时间不得签到 |
| FR-07 | 记录签退时间与提前分钟数，状态转为已完成 |
| FR-08 | 开始后超过宽限期未签到，自动置为违约并释放座位 |
| FR-09 | 座位可置为维修中；有活动预约时禁止直接报修；维修完成可恢复 |
| FR-13 | 基础 5.0 分，每次有效违约扣 0.4 分，下限 1.0 分；逾期记录满 90 天不再计入 |
| FR-14 | 记录限制原因、期限与解封日期；到期自动恢复 |

**业务规则**

| 编号 | 原文 |
| --- | --- |
| BR-01 | 同一座位同一时段至多一条有效预约 |
| BR-02 | 同一学生同一时段不得有多条冲突预约 |
| BR-03 | 维修中的座位不可预约 |
| BR-04 | 有活动预约的座位不可直接报修 |
| BR-05 | 预约状态只能沿允许路径迁移，非法迁移一律拒绝 |
| BR-06 | 取消只允许发生在"已预约"状态 |
| BR-07 | 迟到超过 15 分钟登记违约（参数 15 分钟） |
| BR-08 | 早退只记录分钟数，不扣信用分 |
| BR-09 | 每次有效违约扣 0.4 分，最低 1.0 分 |
| BR-11 | 受限账号可登录、可查看，不可新建预约 |
| BR-12 | 教室容量等于其下实体座位数量 |
| BR-13 | 教室存在非维修座位时为开放状态 |

| BR-15 | 单次 ≤4 小时、每日 ≤2 次、提前 ≤7 天（候选值，Q-02） |

**状态转换**

| 编号 | 原文 |
| --- | --- |
| ST-01 | 提交预约：用户可预约＋座位可预约＋时段无冲突 → 已预约；失败返回具体冲突原因，不生成记录 |
| ST-02 | 已预约 + 取消（开始时间之前）→ 已取消，释放座位 |
| ST-03 | 签到：窗口内受理；超过开始 15 分钟仍受理但登记违约 → 使用中，座位置使用中 |
| ST-04 | 已预约 + 宽限期届满未签到（系统）→ 违约；登记违约并释放座位 |
| ST-05 | 签退：当前时间早于结束时间 → 已完成，记录提前分钟 |
| ST-06 | 使用中 + 管理员判定使用异常 → 违约；登记原因并释放座位，同一预约只登记一次 |
| ST-07 | 已预约 + 管理员代取消 → 已取消；释放座位，须填写原因 |
| ST-08 | 非法迁移：已完成 → 已预约，拒绝（终态不可回退） |
| ST-09 | 非法迁移：已取消 → 使用中，拒绝（签到无有效占位依据） |
| ST-10 | 座位：可预约 + 学生签到成功 → 使用中 |
| ST-11 | 座位：使用中 + 签退或预约结束 → 可预约 |
| ST-12 | 座位：可预约 + 报修（无活动预约）→ 维修中 |
| ST-13 | 座位：维修中 + 维修完成（填写恢复说明）→ 可预约 |
| ST-14 | 座位：维修中 + 再次报修 → 状态保持，不重复登记 |

| 编号 | 原文 |
