## 二、查看顺序

按 P0 → P1 → P2 → P3 → P4 → P5 顺序看，正好走完一个学生的完整闭环：

1. **P0**：学生登录；黑名单账号被拦下，提示里没有解封日期 —— 这是 PV-01 的失败点，也是 V-06 的来源。
2. **P1**：筛选教室、日期、时段，座位卡片用四种颜色区分空闲 / 已预约 / 使用中 / 停用。
3. **P2**：选座后进确认弹窗；本页画的是**冲突态**——红色提示条说明"该座位在该时段已被预约（FR-03 / BR-01）"，提交按钮保持禁用。
4. **P3**：我的预约，四行分别对应已预约、使用中、已完成、已取消四种状态，操作按钮随状态变化。
5. **P4**：签到结果两态——成功进入"使用中"；失败（超出签到窗口）提示预约将转为违约。
6. **P5**：管理员关闭场地，弹窗先列出受影响的 3 条预约，要求填写原因后才允许确认。

## 三、这份原型是什么、不是什么

- **是**：按需求规格 v2.0 的页面结构画的线框，用来在"没有可运行界面时"检查信息是否齐全、操作是否连贯、提示是否明确。
- **不是**：不是截图，不能执行任何规则。纸面原型上"冲突提示"画得再清楚，也不代表后台真的拦得住并发（那是 V-02 的结论，来自代码审读，不是来自这六张图）。

因此 A.6 的结论一律写「通过，纸面原型走查」，**不写**「通过，功能验证」——后者需要实际运行系统并留证据。

## 四、改图后要同步的地方

1. 改 `report/build/figs_proto.py` → 重跑 → 重新导出 PNG 覆盖本目录；
2. 同步替换 `../图源_原型页面.pptx`；
3. 若页面顺序或数量变了，回改 `02_需求分析质量验证报告.md` 的 A.6（基本信息表的"可走查页面"、六个 PV 的"证据位置"）与本 README 的表格。
