## 1. 项目概述

### 1.1 建设目标

系统面向校内自习室预约场景，提供座位查询、预约、取消、签到、签退、维修、投诉、信用和运营分析等功能。当前实现重点是让“座位资源—预约记录—使用状态—异常记录—信用影响”形成可查询、可管理的闭环。

### 1.2 技术实现

| 层次 | 当前实现 | 主要文件 |
| --- | --- | --- |
| 前端 | 原生 HTML、CSS、JavaScript 单页应用 | `app/static/app.js`、`app/static/style.css`、`app/static/overrides.css` |
| 后端 | FastAPI 路由、Pydantic 请求模型 | `app/main.py` |
| 数据库 | SQLite 本地文件数据库，启动时自动建表与迁移 | `app/study_room.db` |
| 运行环境 | Python 3.11+、uv、Uvicorn | `pyproject.toml`、`README.md` |
| 公共项目页 | GitHub Pages 静态介绍页 | `index.html`、`.github/workflows/pages.yml` |

### 1.3 系统边界

当前版本已经包含：

- 学生和管理员两种业务角色。
- 教室、实体座位和座位状态管理。
- 预约创建、查询、取消、签到、签退和违约处理。
- 座位报修、停用和维修完成恢复。
- 学生投诉、报修、建议和账号申诉。
- 履约信用分、信用恢复和黑名单通知。
- 预约趋势、区域分布、热门座位和爽约率统计。
- 学生资料管理和 CSV 批量导入。

当前版本不包含：

- 校园统一身份认证、真实权限令牌和服务端鉴权。
- 定位、二维码、人脸识别等现场验证。
- 支付、押金、门禁和硬件联动。
- 独立课时表、审计日志表和通知投递表。
- 原生移动客户端和完整离线能力。

### 2.1 权限现状风险

当前登录通过本地 `localStorage` 保存角色和用户信息，后端接口没有统一的身份令牌、会话校验和角色中间件。前端会按角色显示不同页面，但直接请求管理员接口时缺少服务端授权拦截。

**结论：角色界面隔离已实现，服务端权限隔离尚未实现。**

### 3.1 预约限制说明

当前代码没有强制实现原报告中的以下候选规则：

- 单人单次预约不超过 4 小时。
- 每人每日最多 2 次预约。
- 最多提前 7 天预约。
- 开始前 30 分钟签到窗口。
- 开始后 15 分钟自动释放的定时任务。

其中“开始后 15 分钟”目前用于判断迟到是否产生违约；超过预约结束时间后无法签到。

## 5. 状态模型

### 5.1 预约状态

```text
booked（已预约）
├── checked_in（使用中）
│   ├── completed（已完成）
│   └── violation（违约）
├── cancelled（已取消）
└── violation（违约）
```

- `booked`：预约已创建，等待签到。
- `checked_in`：已签到，座位进入使用中。
- `completed`：已签退，记录签退和提前分钟数。
- `cancelled`：开始前取消，释放座位。
- `violation`：未签到或使用异常，生成违约记录并影响信用。

### 5.2 座位状态

```text
open（可预约）
├── occupied（使用中）
└── maintenance（维修中）
```

- `open`：可以被预约和签到。
- `occupied`：有用户完成签到。
- `maintenance`：暂停预约；有活动预约时禁止直接切换。
- 维修结束后由管理员恢复为 `open`。

### 5.3 与原报告状态模型的差异

原报告中的“已释放”和“管理员取消”在当前代码中统一映射为：

- “已释放”使用 `violation` 表示，并生成违约记录。
- “管理员取消”复用 `cancelled`，没有单独状态。
- 没有独立“关闭教室”状态，教室开放状态根据座位维修情况自动汇总。

## 6. 数据需求

| 数据表 | 主要字段 | 用途 |
| --- | --- | --- |
| `users` | 姓名、学号、手机号、密码、违约次数、信用分、黑名单信息 | 学生与账号状态 |
| `classrooms` | 名称、楼栋、楼层、容量、状态、设施 | 教室管理 |
| `rooms` | 座位编号、教室关联、容量、状态、设施、维修说明 | 实体座位管理 |
| `bookings` | 用户、座位、起止时间、状态、签到时间、签退时间、迟到/早退分钟 | 预约生命周期 |
| `complaints` | 用户、关联座位、分类、主题、内容、状态、回复 | 投诉建议与报修 |
| `violations` | 用户、预约、原因、来源、时间 | 履约信用依据 |

### 6.1 数据完整性风险

- 预约唯一性目前依赖应用层“先查询再写入”，缺少数据库唯一索引或事务锁。
- 密码以明文保存在 SQLite 中，只适合课程演示。
- 没有独立审计日志表和通知记录表。
- 时段直接保存在预约记录中，没有单独的时间片实体。

## 7. 接口与对接

### 7.1 后端接口

当前后端共有 26 个路由，主要分为：

- 登录与密码：2 个。
- 总览与统计：2 个。
- 教室管理：4 个。
- 座位查询与维修：2 个。
- 预约管理：3 个。
- 用户、账号与信用：6 个。
- 违约记录：2 个。
- 投诉反馈：3 个。
- 静态首页与 CSV 导入：2 个。

### 7.2 前后端数据交换

- 前端通过 `fetch` 调用 JSON API。
- 登录结果写入 `localStorage.studySession`。
- 页面每 10 秒自动刷新一次数据。
- 输入中的投诉表单会暂时阻止自动刷新覆盖内容。
- 静态资源使用版本查询参数，避免浏览器继续加载旧脚本。

### 7.3 部署现状

- FastAPI 和 SQLite 需要在本机或服务器运行。
- GitHub Pages 当前只部署根目录的静态项目介绍页，不能直接运行后端。
- 不修改全局 Git 代理配置；代理仅用于当前 Git 命令。

| AnalyticsController | 运营统计和热门座位分析 | `refreshSeconds = 10` | `overview(): Map`；`analytics(): Analytics`；`popularSeats(): List<SeatStat>` | 汇总总览；计算趋势、区域分布、热门座位和爽约率 |

### 8.4 Boundary 层类详细说明

**表 3-2-3　Boundary 层类详细说明**

| 类名 | 作用 | 关键属性 | 核心方法 | 方法作用 |
| --- | --- | --- | --- | --- |
| LoginBoundary | 登录界面 | `role: string` | `showLogin(): void`；`submitLogin(account, pwd): Session`；`showError(message): void` | 切换学生/管理员登录；提交账号密码；显示登录错误 |

### 8.5 类关系

- `Student`、`Admin` 继承 `User`。
- `Classroom` 与 `Seat` 为一对多聚合关系。
- `Student` 与 `Reservation` 为一对多关系。
- `Seat` 与 `Reservation` 为一对多关系。
- `Student` 与 `Complaint` 为一对多关系，`Complaint` 可选关联一个 `Seat`。
- `Student` 与 `Violation` 为一对多关系，`Violation` 可选关联一个 `Reservation`。
- `CreditProfile` 根据 `Student` 和 `Violation` 实时派生。
- Boundary 通过 JSON API 调用 Control，Control 读写 Entity。

## 12. 风险与优化优先级

### 高优先级

1. 增加服务端登录会话和角色鉴权，禁止学生直接调用管理员接口。
2. 为预约冲突增加数据库唯一约束或事务控制，补齐并发场景。
3. 增加密码哈希、敏感字段脱敏和数据保留规则。
4. 建立可重复运行的自动化测试，替代仅靠人工走查。
5. 明确超时未签到的自动扫描任务和部署方式。

### 中优先级

1. 补齐单次时长、每日次数和提前预约天数限制。
2. 增加审计日志和通知记录表。
3. 增加真正的关闭教室及批量预约处置接口。
4. 完善移动端和键盘可访问性测试。
5. 分离演示环境配置和正式环境配置。

## 13. 结论

当前系统已经具备可运行的课程演示闭环，页面、接口和数据库能够共同完成预约、签到、签退、维修、投诉、信用和运营统计。

本次代码对齐后的需求报告不再把信用分、投诉、黑名单和维修列为“范围外功能”，而是把它们作为已实现功能纳入验收范围；同时明确保留服务端鉴权、并发约束、审计日志、通知投递和自动化测试等未完成事项，避免报告与代码现状不一致。
